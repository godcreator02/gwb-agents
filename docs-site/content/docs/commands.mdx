**本页回答**：五条公开命令各收什么参数、回什么、什么情况下报错。每条命令只查参数形状，然后调服务 `gwbZcode` 的同名方法，参数与回执和方法一样；别的插件直接 inject 服务，不经命令。派任务的两条 `effect` 是 `external`：指令经 ZCode 发给外部的模型服务，ZCode 还会以完全访问权限改本机文件；
`zcode.open` 改 ZCode 窗口显示的工作区，标 `write`；`zcode.status` 只读快照，标 `read`；`zcode.archive` 改 ZCode 的任务索引，标 `write`。
五条命令都要 ZCode 带 `--remote-debugging-port=9339` 启动：插件只连这个端口，不开也不关；命令结束断开自己的连接，不影响其他 home。

一次派任务的流程：要让人在侧栏里看见就先 `open` 那个目录 → `create`（或 `send`）拿到 `taskId` 与 `waitCommand` → Monitor 在后台等 `waitCommand` 打出结束那一行 → `status` 读回答 → 不再用的会话 `archive`。要不要回报、报给谁由派任务的一方写进任务说明，这些命令不参与。

## zcode.open

把 ZCode 窗口切到一个工作区。侧栏只显示当前工作区的会话：`zcode.create` 在哪个目录建会话，人就要切到哪个目录才看得见。

{/* ref file="../plugins/zcode/src/args.ts" lines="38-42" hash="cb4987665526" blob="ed4e0f1e507f" */}

| 参数 | 必给 | 说明 |
| --- | --- | --- |
| `workspace` | 是 | 工作区目录的绝对路径，要已存在 |

回 `{ workspace, switched }`：`switched` 为 `false` 表示窗口本来就在这个工作区，没有动。路径比较不分大小写、不管结尾的分隔符。

## zcode.create

在一个工作区里新建会话、切到完全访问、发出任务，等这一轮在 ZCode 里开始了就交回。

{/* ref file="../plugins/zcode/src/args.ts" lines="44-51" hash="1dff313b8054" blob="ed4e0f1e507f" */}

| 参数 | 必给 | 说明 |
| --- | --- | --- |
| `workspace` | 是 | 工作区目录的绝对路径，要已存在。ZCode 在这个目录里执行任务，侧栏里会话归在这个工作区下 |
| `prompt` | 是 | 任务说明，非空。回报约定（如有）由发起方写进这里，本插件不另收回报参数 |

同一个工作区可以同时开几条会话，本插件不管占用；会不会改到同一个文件由派任务的一方安排。

## zcode.send

在已有会话里接着发指令。`task` 是 `zcode.create` 回执里的 `taskId`，`workspace` 写建它时的那个目录；发之前同样切到完全访问——
人在界面上把模式改过了也会被切回来。

{/* ref file="../plugins/zcode/src/args.ts" lines="53-63" hash="1116975434dc" blob="ed4e0f1e507f" */}

| 参数 | 必给 | 说明 |
| --- | --- | --- |
| `workspace`、`task` | 是 | 建会话时的目录与 `taskId` |
| `prompt` | 是 | 指令，非空 |
| `interrupt` | 否 | 布尔。缺省：会话还在跑时，新指令排在这一轮后面，这一轮做完才读到。`true`：不排队，当场取消正在跑的命令或工具调用（子进程被结束），用这条指令开新的一轮，前面的上下文还在；同界面上排队消息的「立即」 |

`interrupt` 用来中途纠正派出去的任务：发出去的说明写漏了、它卡在一条没用的命令上，排队要等整个任务做完才送得到。
正在跑数据迁移、写盘这类中途打断会留下半截结果的命令时别用。

两条派任务的命令回执相同：

{/* ref file="../plugins/zcode/src/commands.ts" lines="7-11" hash="e73db2a83b4d" blob="293cca35c037" */}

| 字段 | 说明 |
| --- | --- |
| `taskId` | 会话 id（`sess_` 开头），之后给 `zcode.status` 与 `zcode.send` |
| `title` | 侧栏里显示的标题，ZCode 自己起，可能在第一轮之后改 |
| `status` | ZCode 的任务状态，刚发出时通常是 `running` |
| `mode` | 代理进程实际用的权限模式，总是 `yolo` |
| `roundStarted` | `false` 表示 30 秒内这一轮还没开始（多半排在同一会话还在跑的上一轮后面），这时 `zcode.status` 读到的仍是上一轮 |
| `waitCommand` | 一条命令行，在 Claude Code 里原样交给 Monitor 工具在后台等这一轮结束，见下面「在后台等结束」 |

### 在后台等结束

`waitCommand` 运行本包的等待脚本 `dist/wait-round.js`，参数是一段 base64url（工作区、会话、home 名与 gwb-mcp 命令行客户端的路径），bash 与 pwsh 都能原样运行。
脚本经这个 home 的 gwb-mcp 命令行客户端循环调 `zcode.status`（每次等 60 秒），等的过程中不输出任何东西；Monitor 把每一行输出当一次通知，所以只会收到一行。
客户端没交回回执（超过它的 HTTP 时限、连不上 MCP 入口）时脚本隔 10 秒再查，连续 5 次才报错，几个会话同时等不会因为单次查询慢而中断：

| 那一行 | 意思 |
| --- | --- |
| `ZCODE-ROUND-OVER {taskId,status,mode,pendingPermissions,lastReplyTail}` | 这一轮停下了（`roundIsOver` 为 `true`），退出码 0。`lastReplyTail` 是最后一条回答压成一行后的末尾 600 字，完整回答用 `zcode.status` 读 |
| `ZCODE-WAIT-FAILED <原因>` | 等不下去了，退出码 1：home 里没装 gwb-mcp、`zcode.status` 交回了失败回执（原因原样带上）、连续 5 次没交回回执、参数不对 |

Monitor 单次最长 30 分钟，到时限还没等到就用同一条 `waitCommand` 再开一个。`roundStarted` 为 `false` 时等到的是上一轮结束，收到后用 `zcode.status` 核对 `replies`。
没有 Monitor 的客户端照旧用 `zcode.status` 带 `waitSeconds` 轮询。

## zcode.status

读一个会话最新一轮（最后一条用户消息之后）的进度与回答。

{/* ref file="../plugins/zcode/src/args.ts" lines="65-76" hash="1de839998cd6" blob="ed4e0f1e507f" */}

{/* ref file="../plugins/zcode/src/checks.ts" lines="16-24" hash="ab1bc4849587" blob="46c2c86d4f9d" */}

| 参数 | 必给 | 说明 |
| --- | --- | --- |
| `workspace`、`task` | 是 | 同 `zcode.send` |
| `waitSeconds` | 否 | 缺省 0 立即交回；给了就最多等这么久（0 到 240），做完提前交回 |
| `replyTailChars` | 否 | 正整数：只交回回答末尾这么多个字符；缺省全部交回 |

ZCode 会把这一轮的工具调用记录（工具名、输入、输出）也写进回答，看图、读长文件多的一轮，一条回答就有几万字，
超过 MCP 入口单次返回的上限（40000 字符），整个回执交不回来。收尾的总结在最后，所以截的是末尾：从最后一条回答往前留，
合计不超过 `replyTailChars`，越过上限的那一条只留它的末尾，再往前的整条省掉。

{/* ref file="../plugins/zcode/src/task-progress.ts" lines="93-108" hash="0ed3b2279759" blob="4e0b14d7e847" */}

| 字段 | 说明 |
| --- | --- |
| `roundIsOver` | `true` 才是这一轮停下了：做完、失败，或停在等人确认 |
| `status` | ZCode 的任务状态：`completed`、`idle` 是正常结束，`failed`、`error`、`cancelled` 是失败，`running` 还在跑；没发过指令的会话是 `null` |
| `replies` | 这一轮的回答，按出现顺序；没做完时是写到一半的内容 |
| `omittedReplyChars` | 按 `replyTailChars` 省掉的字符数；没给这个参数或没省是 0 |
| `mode` | 代理进程实际用的权限模式 |
| `fileChanges` | ZCode 记录的文件改动，原样带回 |
| `pendingPermissions` | 非空表示停在等人确认，要去 ZCode 界面处理 |

## zcode.archive

把一个会话从 ZCode 侧栏的会话列表里收起来，记录不删，在 ZCode 的已归档列表里还看得到。参数 `workspace`、`task` 同 `zcode.send`，
只是 `workspace` 那个目录已经删了也行：它只是 ZCode 记会话用的键，归档不在目录里执行任何东西。

{/* ref file="../plugins/zcode/src/args.ts" lines="78-85" hash="3ea413b42ce3" blob="ed4e0f1e507f" */}

回 `{ taskId, title, archived: true }`。还在跑（`status` 为 `running`）的会话直接报错，等 `zcode.status` 的 `roundIsOver` 为 `true` 再归档；
已经归档过的再调一次照样成功。

## 报错

命令执行失败时回 `ok: false`（经 MCP 入口是 `isError` 的文本），原因写在文本里：

| 原因文本里有 | 怎么办 |
| --- | --- |
| `不认识参数`、`缺 …`、`要是绝对路径`、`不是已存在的目录`、`waitSeconds`、`replyTailChars` | 照文本改参数 |
| `zcode.status` 的返回超过单次返回的上限 | 带上 `replyTailChars`（如 20000）再调 |
| `应有一个 ZCode 主进程` | ZCode 没开，或开了多个实例：请用户打开或关掉多余的 |
| `ZCode 不是带 --remote-debugging-port=9339 启动的` | 请用户关掉 ZCode，照文本里的命令带参数重开；ZCode 自动更新后重启也会这样 |
| `命令行带着 --remote-debugging-port=9339，但 … 连不上` | 端口被别的程序先占了，或 ZCode 还没启动完：稍后再调，仍不行请用户重开 ZCode |
| `应有一个 ZCode 工作区窗口` | 请用户关掉多余的 ZCode 窗口 |
| `找不到 services.…`、`快照形状不对`、`没有 settings.mode.current`、`没回 taskId`、`activeWorkspacePath 应有一个值` | ZCode 升级改了内部结构，插件要跟着改 |
| `秒后窗口的工作区仍是` | ZCode 没按启动参数切过去，可能改了启动参数的处理；请用户手动切 |
| `切换到完全访问 … 后代理的模式是` | 模式没切成，指令没发出 |
| `收下了这条指令，但没有立即发出` | 带 `interrupt` 时 ZCode 没按立即投递，指令已经按回执里写的方式（多半是排队）收下；不要重发 |
| `localStorage 里没有 zcode-v4-client-id:v1` | ZCode 升级改了内部结构，`interrupt` 要跟着改 |
| `还在跑，等这一轮做完 … 再归档` | 用 `zcode.status` 等它做完再 `zcode.archive` |
| `调过 archiveTask 之后不在 … 的已归档列表里` | `workspace` 不是建这个会话时的目录，或 ZCode 改了归档的做法 |
| `调试协议请求 … 无响应` | 先去 ZCode 侧栏看指令有没有发出去，再决定要不要重调 |
