**本页回答**：这个插件做什么、它和 agent、ZCode 桌面端之间的每条接缝传什么、由谁负责、怎么测，以及它刻意不做什么。

ZCode 是本机装的另一个 AI 编程客户端（Electron 桌面端，模型走用户的 GLM 套餐）。把批量的活派给它，能省下派活一方自己的模型额度。
ZCode 没有给外部用的建任务入口：深链接只能打开工作区，本机也没有它的接口端口；能让任务出现在侧栏里、人看得见的，只有它客户端窗口里
自己的服务。所以这个插件打开 ZCode 主进程的 Node 调试端口，在窗口里执行脚本调这些服务——
这条路怎么找到的、为什么不用 CLI 无界面或定时自动化，见轨迹区。

插件只有一个包 `@godcreator/gwb-zcode`（`plugins/zcode/`，入口 `src/index.ts`），四条命令：`zcode.create` 新建会话发任务、
`zcode.send` 在已有会话里接着发，两条都先把会话切到「完全访问」、发出去就返回；`zcode.status` 读一个会话最新一轮做完没有、回答是什么；
`zcode.archive` 把做完的会话从侧栏收起来。

## 接缝逐条

### 1 agent → 插件

agent 经 MCP 入口 `run` 调四条命令，参数形状写在登记时的 `usage` 里。参数只在这一层校验，认不出的键直接报错——比如多给一个
`mode` 不会被悄悄忽略，权限只有完全访问一种：

{/* ref file="../plugins/zcode/src/args.ts" lines="27-34" hash="a79674b46996" blob="9c9c6bdf9e1f" */}

`workspace` 要是已存在目录的绝对路径，这一条在登记命令的地方查（它要读磁盘）；`zcode.archive` 不查目录在不在，目录删了的旧会话也要能收起来：

{/* ref file="../plugins/zcode/src/index.ts" lines="19-21" hash="a3bef6297dfa" blob="5ec367b6c96e" */}

**没有一条命令会一直等到 ZCode 做完。**MCP 客户端等一次调用有上限，Claude Code 是 300 秒没有动静就放弃，而 ZCode 干一个活常常超过这个时间。
所以 `create` / `send` 发出就返回，`status` 的 `waitSeconds` 最多 240 秒、做完提前交回，agent 隔一阵问一次（轨迹卡[「发出即返回」](/trajectory/2026-10-02-dispatch-then-poll)）：

{/* ref file="../plugins/zcode/src/args.ts" lines="5-6" hash="6cd8bf19180a" blob="9c9c6bdf9e1f" */}

测试：`tests/args.test.ts`。

### 2 插件 → 进程表

调试端口要开在 ZCode 主进程上，先找到它的 pid。ZCode 一开就是十几个 `ZCode.exe`（渲染进程、GPU 进程、每个会话一个 `zcode.cjs app-server`），
主进程是命令行里没有 `--type=`、`zcode.cjs`、`windows-helper` 的那一个。剩下不是恰好一个就报错，不猜：

{/* ref file="../plugins/zcode/src/desktop.ts" lines="15-17" hash="fcb66fbc34fb" blob="1cb48af3256e" */}

没有自动测试：要真的开着 ZCode。在隔离 home 里调命令验证。

### 3 插件 → 主进程（调试端口）

ZCode 主进程是 Electron 里的 Node。9229 端口没开时，`process._debugProcess(pid)` 让它在不重启的情况下打开调试端口；开了以后经 WebSocket 发
`Runtime.evaluate`。只有自己打开的端口，结束时才关掉——端口原来就开着（比如有人在调试 ZCode）就不动它：

{/* ref file="../plugins/zcode/src/desktop.ts" lines="64-83" hash="8ff492e0d767" blob="2a7faa4a7dd6" */}

连上后先核对端口确实属于刚才找到的那个 pid，别的程序占着 9229 就报错：

{/* ref file="../plugins/zcode/src/desktop.ts" lines="141-143" hash="444caa77a869" blob="2a7faa4a7dd6" */}

**几条命令同时跑时共用一个连接**，最后一条结束才关端口。各自开关的话，先结束的那条会把别人正在用的端口关掉；关端口在 ZCode 那边是
200 毫秒后才真正生效，正在关的时候来了新命令，要等它关完再重新打开：

{/* ref file="../plugins/zcode/src/desktop.ts" lines="159-194" hash="97e43b6351a5" blob="2a7faa4a7dd6" */}

关端口失败只写一行告警日志、不让命令报错：那时任务已经发出去了，报错会让调用方拿不到 `taskId`。没有自动测试。

### 4 主进程 → 工作区窗口

在主进程里取 Electron 的 `BrowserWindow`，按页面地址认出工作区窗口，必须恰好一个：

然后在那个窗口里 `executeJavaScript`，从 React 的根节点沿 fiber 树广度优先找到 `memoizedProps.services` 下的服务，调它的方法，

### 5 窗口 → 会话

`createTask` 必须带 `v4Create: true`，否则走旧的创建流程，发指令时报数据库关联错误；给它传 `mode` 不起作用：

{/* ref file="../plugins/zcode/src/round.ts" lines="29-33" hash="329cae0cbfd0" blob="1835c595758d" */}

**完全访问以代理进程为准。**代理实际用的模式在 `zcodeAgentService.readSession` 的 `settings.mode.current`；任务的 `meta.mode`（侧栏与界面显示的那个）
只在代理的模式真的变了时才更新，会落后——新会话继承到工作区上次用的 `yolo`、跑过的会话放一阵子再恢复，都可能代理是 `yolo`、界面显示「变更前确认」。
每次发指令前代理不是 `yolo` 就切，切完读回还不是就不发；显示落后时只在会话没在跑的时候先切 `build` 再切 `yolo` 让它跟上，
跑着的时候切到 `build`，那一瞬间的工具调用会停下等确认（轨迹卡[「模式与收尾信号」](/trajectory/2026-10-02-mode-and-round-signals)、
[「显示模式会落回」](/trajectory/2026-10-02-displayed-mode-drifts)）：

{/* ref file="../plugins/zcode/src/round.ts" lines="35-56" hash="4741228ff8df" blob="1835c595758d" */}

**发出后等这一轮开始了才交回。**`status` 把「最新一轮」切在最后一条用户消息上，刚发出的一两秒里快照还是上一轮；所以 `send` 每 0.5 秒读一次，
看到这一轮的提问出现了才交回，30 秒还没出现（多半排在还在跑的上一轮后面）就先交回、带 `roundStarted: false`：

{/* ref file="../plugins/zcode/src/round.ts" lines="68-92" hash="533d74f378a3" blob="1835c595758d" */}

**判断这一轮做完的难点在于 `status` 落后于消息**：转成 `completed` 时回答可能还没写进快照，而一轮里的回答按同一个消息 id 越写越长、写完才带上 `durationMs`。
所以状态是结束类的、并且这一轮的助手消息都有 `durationMs` 才算做完；失败类状态不等回答；停在等人确认权限时也算停下了（完全访问下不该出现，出现了就是哪里不对）：

{/* ref file="../plugins/zcode/src/task-progress.ts" lines="68-91" hash="7fa1e134fb83" blob="32ed56e8d12c" */}

`status` 的 `mode` 同样报代理的模式，不报会落后的显示值：

{/* ref file="../plugins/zcode/src/round.ts" lines="94-105" hash="c56d6db6f860" blob="1835c595758d" */}

**归档用 `archiveTask`。**侧栏索引里那条的 `archived` 变成 1，会话记录不删。它的返回里没有 `archived`，所以归档后用 `listArchivedTasks` 看这条在不在已归档列表里；
还在跑的会话不归档、直接报错，归档后它从侧栏消失，人就看不见它还在干活（轨迹卡[「加归档」](/trajectory/2026-10-02-archive-sessions)）：

{/* ref file="../plugins/zcode/src/archive.ts" lines="14-28" hash="3cdc7d0478aa" blob="956c72817d7c" */}

快照来自 ZCode 内部接口，形状不对直接报错，不按缺省值往下跑。测试：`tests/task-progress.test.ts`，按实测的顺序覆盖一轮里快照的几个阶段：

## 对外能做什么

`zcode.create` 在一个工作区里新建会话、发任务；`zcode.send` 在已有会话里接着发；`zcode.status` 读最新一轮的进度与回答；`zcode.archive` 归档一个会话。
逐条的参数与回执在[命令](/docs/commands)，
peer 写法在[插件之间怎么连](/docs/wiring)。

## 依赖谁

| 依赖 | 用来做什么 | 缺了会怎样 |
| --- | --- | --- |
| 命令总线 `gwb-commands`（必需） | 登记四条命令 | 插件不加载 |
| 说明书 `gwb-skills`（局部注入） | 登记说明书 `zcode` | 照常加载；agent 读不到说明书 |
| 内核包 `gwb-kernel-desktop` | 接口类型 | — |
| ZCode 桌面端（本机安装、开着） | 一切：建会话、切模式、发指令、读快照 | 命令报「应有一个 ZCode 主进程」 |
| `pwsh` | 列进程找 ZCode 主进程 | 命令报「找 ZCode 主进程失败」 |

## 不做的事

- **不提供别的权限模式**：一律完全访问，没有模式参数（轨迹卡[「一律完全访问」](/trajectory/2026-10-02-full-access-only)）
- **不一直等到 ZCode 做完**：发出即返回，结果用 `zcode.status` 查（轨迹卡[「发出即返回」](/trajectory/2026-10-02-dispatch-then-poll)）
- **不取消任务、不列会话、不取消归档**：只做派活、查结果、归档
- **不归档还在跑的会话**：归档后人就看不见它在干活
- **不用 ZCode 的 CLI 无界面模式**：会话不进侧栏，人看不见（轨迹卡[「要侧栏可见」](/trajectory/2026-10-02-desktop-visible-over-cli)）
- **不借定时自动化派任务**（轨迹卡[「不借定时任务」](/trajectory/2026-10-02-no-automation-detour)）
- **不支持多个 ZCode 实例或多个工作区窗口**：遇到就报错，不替调用方挑
- **不启动 ZCode**：没开就报错，由人打开
