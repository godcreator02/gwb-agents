import { ZcodeSeams } from './zcode/zcode-seams'

**本页回答**：这个插件做什么、它和 agent、ZCode 桌面端之间的每条接缝传什么、由谁负责、怎么测，以及它刻意不做什么。

ZCode 是本机装的另一个 AI 编程客户端（Electron 桌面端，模型走用户的 GLM 套餐）。把批量的任务交给它，能省下派任务一方自己的模型额度。
ZCode 没有给外部用的建任务入口：启动参数与深链接只能打开工作区，本机也没有它的接口端口；能让任务出现在侧栏里、人看得见的，只有它客户端窗口里
自己的服务。所以 ZCode 要带 `--remote-debugging-port=9339` 启动，这个插件连上窗口页面的远程调试端口，在窗口里执行脚本调这些服务——
这条路怎么找到的、为什么不用 CLI 无界面或定时自动化，见轨迹区。

ZCode 插件对应包 `@godcreator/gwb-zcode`（`plugins/zcode/`，入口 `src/index.ts`）。本体是 cordis 服务 `gwbZcode`，五个方法：`open` 把窗口切到一个工作区，
侧栏只显示当前工作区的会话，要让人看见新会话就先切过去；`create` 新建会话发任务、
`send` 在已有会话里接着发，两个都先把会话切到「完全访问」、发出去就返回；`status` 读一个会话最新一轮做完没有、回答是什么；
`archive` 把做完的会话从侧栏收起来。别的插件 inject 这个服务调方法；进程外的 agent 用同名的 `zcode.*` 命令，命令只查参数形状、再调同一个方法。

### 1 调用方 → 插件

两种调用方走两条入口，背后是同一份实现。**别的插件**（qq-bot、协作站）inject 服务 `gwbZcode` 调方法，有类型、出错直接抛异常；服务名与方法签名就是本包给 cordis `Context` 补的那一项，类型从本包的 `dist/index.d.ts` 取：

**进程外的 agent** 经 MCP 入口 `run` 调 `zcode.*` 命令。命令是服务方法的薄封装：只查参数形状（认不出的键直接报错，比如多给一个 `mode` 不会被悄悄忽略，权限只有完全访问一种），然后调同名方法：

{/* ref file="../plugins/zcode/src/args.ts" lines="9-16" hash="a79674b46996" blob="9f5f8a9bc7ec" */}

{/* ref file="../plugins/zcode/src/commands.ts" lines="42-42" hash="92493ad22dbb" blob="293cca35c037" */}

取值的含义两条入口都要查，所以放在服务方法里：`workspace` 要是已存在目录的绝对路径（它要读磁盘）；`archive` 只查是不是绝对路径，目录删了的旧会话也要能收起来：

{/* ref file="../plugins/zcode/src/checks.ts" lines="11-14" hash="d43a8e7161ff" blob="46c2c86d4f9d" */}

**没有一个方法会一直等到 ZCode 做完。**MCP 客户端等一次调用有上限，Claude Code 是 300 秒没有动静就放弃，而 ZCode 做一个任务常常超过这个时间。
所以 `create` / `send` 发出就返回，`status` 的 `waitSeconds` 最多 240 秒、做完提前交回（轨迹卡[「发出即返回」](/trajectory/2026-10-02-dispatch-then-poll)）。
Claude Code 里的 agent 不用自己隔一阵问一次：回执里的 `waitCommand` 交给 Monitor 在后台等，见接缝 7：

{/* ref file="../plugins/zcode/src/api.ts" lines="8-9" hash="ce72ed6731b8" blob="105f68ba60a1" */}

测试：`tests/args.test.ts`（参数形状）、`tests/checks.test.ts`（取值）。

### 3 插件 → 工作区窗口（远程调试端口）

9339 是 Chromium 的远程调试端口，`/json/list` 列出 ZCode 打开的每个页面。按类型 `page`、地址含 `/out/renderer/index.html` 认出工作区窗口，必须恰好一个：

{/* ref file="../plugins/zcode/src/desktop.ts" lines="103-109" hash="1acde85549fa" blob="4d4211325757" */}

连上这个页面的 WebSocket，发 `Runtime.evaluate` 直接在页面里执行：从 React 的根节点沿 fiber 树广度优先找到 `memoizedProps.services` 下的服务，调它的方法，
返回值按 JSON 带回。用到两个服务：`zcodeTaskService` 管任务（侧栏里的一条），`zcodeAgentService` 管会话背后的代理进程。
**这一段完全依赖 ZCode 的内部结构**：React 树里服务放在哪个组件的属性上、服务叫什么，ZCode 升级都可能改，找不到时报错写明是这里：

{/* ref file="../plugins/zcode/src/desktop.ts" lines="42-52" hash="ec001d7bb4d6" blob="4d4211325757" */}

{/* ref file="../plugins/zcode/src/desktop.ts" lines="195-196" hash="0e94304281e9" blob="4d4211325757" */}

端口归 ZCode 进程所有，随它退出关闭，可能同时被多个 home 或调试器使用。**同一 home 的并发命令共用一个连接**，最后一条结束只断开自己的 WebSocket；
不同 home 各用自己的连接，一个机器人完成查询不会中断另一个的派发回执：

{/* ref file="../plugins/zcode/src/desktop.ts" lines="215-250" hash="a46299878854" blob="4d4211325757" */}

清理连接失败只记告警、不盖过成功回执。WebSocket 断线立即拒绝正在等待的请求、清掉超时计时器；不自动重发任何指令，避免已经派出去的任务重复执行。
连接与请求都有 30 秒等待上限。`tests/desktop.test.ts` 用两个独立插件实例验证跨 home 并发，验证断线会立即报错，并测只认恰好一个工作区页面。

### 4 窗口 → 会话

`createTask` 必须带 `v4Create: true`，否则走旧的创建流程，发指令时报数据库关联错误；给它传 `mode` 不起作用：

{/* ref file="../plugins/zcode/src/round.ts" lines="31-35" hash="329cae0cbfd0" blob="89568f6fe74d" */}

**完全访问以代理进程为准。**代理实际用的模式在 `zcodeAgentService.readSession` 的 `settings.mode.current`；任务的 `meta.mode`（侧栏与界面显示的那个）
只在代理的模式真的变了时才更新，会落后——新会话继承到工作区上次用的 `yolo`、跑过的会话放一阵子再恢复，都可能代理是 `yolo`、界面显示「变更前确认」。
每次发指令前代理不是 `yolo` 就切，切完读回还不是就不发；显示落后时只在会话没在跑的时候先切 `build` 再切 `yolo` 让它跟上，
跑着的时候切到 `build`，那一瞬间的工具调用会停下等确认（轨迹卡[「模式与收尾信号」](/trajectory/2026-10-02-mode-and-round-signals)、
[「显示模式会落回」](/trajectory/2026-10-02-displayed-mode-drifts)）：

{/* ref file="../plugins/zcode/src/round.ts" lines="37-58" hash="4741228ff8df" blob="89568f6fe74d" */}

**发出后等这一轮开始了才交回。**`status` 把「最新一轮」切在最后一条用户消息上，刚发出的一两秒里快照还是上一轮；所以 `send` 每 0.5 秒读一次，
看到这一轮的提问出现了才交回，30 秒还没出现（多半排在还在跑的上一轮后面）就先交回、带 `roundStarted: false`：

{/* ref file="../plugins/zcode/src/round.ts" lines="93-121" hash="0a9d6e917855" blob="89568f6fe74d" */}

**`interrupt` 不走 `sendPrompt`。**会话还在跑时，`sendPrompt` 发的指令一律排进队列，这一轮做完才读到；`sendPrompt` 也不收投递方式。
所以带 `interrupt` 时直接发会话命令 `sendText`，要求投递方式 `startNow`：ZCode 当场取消正在跑的工具调用、结束它的子进程，用这条指令开新的一轮，
跟界面上排队消息的「立即」效果相同。投递方式另有 `guide`（引导当前任务），实测会话在跑命令时被降成排队，所以不用。
会话命令的信封要带窗口自己的 `clientId`（存在窗口的 `localStorage` 里），别的值宿主报 `fault.command.clientMismatch`。
ZCode 收下了却没按 `startNow` 投递时直接报错，写明它实际怎么投递的，不当成发出去了（探针 `probes/2610071730_send-now`）：

{/* ref file="../plugins/zcode/src/round.ts" lines="70-91" hash="96b75ed4d4a7" blob="89568f6fe74d" */}

**判断这一轮做完的难点在于 `status` 落后于消息**：转成 `completed` 时回答可能还没写进快照，而一轮里的回答按同一个消息 id 越写越长、写完才带上 `durationMs`。
所以状态是结束类的、并且这一轮的助手消息都有 `durationMs` 才算做完；失败类状态不等回答；停在等人确认权限时也算停下了（完全访问下不该出现，出现了就是哪里不对）：

{/* ref file="../plugins/zcode/src/task-progress.ts" lines="68-91" hash="7fa1e134fb83" blob="32ed56e8d12c" */}

`status` 的 `mode` 同样报代理的模式，不报会落后的显示值：

{/* ref file="../plugins/zcode/src/round.ts" lines="123-134" hash="c56d6db6f860" blob="89568f6fe74d" */}

**归档用 `archiveTask`。**侧栏索引里那条的 `archived` 变成 1，会话记录不删。它的返回里没有 `archived`，所以归档后用 `listArchivedTasks` 看这条在不在已归档列表里；
还在跑的会话不归档、直接报错，归档后它从侧栏消失，人就看不见它还在执行（轨迹卡[「加归档」](/trajectory/2026-10-02-archive-sessions)）：

### 7 等待脚本 → 插件（经 MCP 入口）

Claude Code 的 Monitor 工具在后台运行一条命令，把它标准输出的每一行当一次通知，命令退出就结束。`create` / `send` 的回执带上这样一条命令 `waitCommand`，
agent 原样交给 Monitor，不用自己隔一阵调一次 `status`（轨迹卡[「用 Monitor 等结束」](/trajectory/2026-10-16-monitor-wait-round)）。
命令运行本包的第二个产物 `dist/wait-round.js`。脚本与 gwb-mcp 命令行客户端都取 home 的 `node_modules` 下的路径，home 名取 home 目录名：

{/* ref file="../plugins/zcode/src/index.ts" lines="85-98" hash="7e8202af983a" blob="8a722ee3662c" */}

Monitor 可能用 bash 也可能用 pwsh 运行这条命令，两边的引号与转义规则不同。所以脚本路径只用普通双引号括起来，工作区、会话这些参数整个编成一段 base64url：

{/* ref file="../plugins/zcode/src/wait-round.ts" lines="24-34" hash="3617dfca0dad" blob="9ef5398e0c60" */}

脚本经 gwb-mcp 的命令行客户端回到这个 home 的 MCP 入口，循环调 `zcode.status`，每次等 120 秒（客户端的 HTTP 时限放到 150 秒）。等的过程中不输出任何东西，
这一轮停下时打一行 `ZCODE-ROUND-OVER`、出错打一行 `ZCODE-WAIT-FAILED`，然后退出：

{/* ref file="../plugins/zcode/src/wait-round.ts" lines="84-92" hash="c7acfdcd7c1a" blob="9ef5398e0c60" */}

home 里没装 gwb-mcp 时脚本报错退出，隔离 home 的基础插件里没有它，要验证这条路得先装上。
测试：`tests/wait-round.test.ts` 测命令行拼出来能原样读回、参数错了直接报错、结束那一行只有一行；Monitor 整条流程在装了 gwb-mcp 的隔离 home 里验证。

## 对外能做什么

服务 `gwbZcode` 的 `open` 把窗口切到一个工作区；`create` 在一个工作区里新建会话、发任务；`send` 在已有会话里接着发；`status` 读最新一轮的进度与回答；`archive` 归档一个会话。
同名的 `zcode.*` 命令给 agent 用，参数与回执和方法一样，逐条见[命令](/docs/commands)；
服务、注入与 peer 写法在[插件之间怎么连](/docs/wiring)。

## 依赖谁

| 依赖 | 用来做什么 | 缺了会怎样 |
| --- | --- | --- |
| 命令总线 `gwb-commands`（必需） | 登记五条命令 | 插件不加载 |
| `cordis` | 服务基类 `Service` | — |
| 说明书 `gwb-skills`（局部注入） | 登记说明书 `zcode` | 照常加载；agent 读不到说明书 |
| 内核包 `gwb-kernel-desktop` | 接口类型 | — |
| ZCode 桌面端（本机安装、开着，带 `--remote-debugging-port=9339` 启动） | 一切：切工作区、建会话、切模式、发指令、读快照 | 没开报「应有一个 ZCode 主进程」；没带参数报「ZCode 不是带 … 启动的」并写明怎么重开 |
| `pwsh` | 列进程找 ZCode 主进程 | 命令报「找 ZCode 主进程失败」 |
| MCP 入口 `gwb-mcp`（同一个 home 里装着；不写 peer，插件本身不用它） | `waitCommand` 经它的命令行客户端回调 `zcode.status` | 服务与命令照常；等待脚本打一行 `ZCODE-WAIT-FAILED` 退出，改用 `zcode.status` 轮询 |

## 不做的事

- **不提供别的权限模式**：一律完全访问，没有模式参数（轨迹卡[「一律完全访问」](/trajectory/2026-10-02-full-access-only)）
- **不一直等到 ZCode 做完**：发出即返回，结果用 `zcode.status` 查，要在后台等到底就把 `waitCommand` 交给 Monitor（轨迹卡[「发出即返回」](/trajectory/2026-10-02-dispatch-then-poll)）
- **不取消任务、不列会话、不取消归档**：只做切工作区、派任务、查结果、归档
- **不归档还在跑的会话**：归档后人就看不见它在执行
- **不用 ZCode 的 CLI 无界面模式**：会话不进侧栏，人看不见（轨迹卡[「要侧栏可见」](/trajectory/2026-10-02-desktop-visible-over-cli)）
- **不借定时自动化派任务**（轨迹卡[「不借定时任务」](/trajectory/2026-10-02-no-automation-detour)）
- **不支持多个 ZCode 实例或多个工作区窗口**：遇到就报错，不替调用方挑
- **不启动、不重启 ZCode**：没开、没带调试参数都报错，由人打开或重开；`zcode.open` 先确认主进程在，才运行第二个实例转交启动参数
- **`create` 不替调用方切工作区**：切窗口会打断人正在看的界面，要不要切由调用方用 `open` 决定
- **不管占用**：同一个工作区可以同时开几条会话（批量派活就是同一目录几条并行），会不会改到同一个文件由派任务的一方安排（轨迹卡[「删掉占用表」](/trajectory/2026-10-07-drop-workspace-occupancy)）
- **不参与回报**：要不要回报、报给谁，由派任务的一方写进任务说明；本插件不保存凭证、不转发结果，也不认识任何上层应用
